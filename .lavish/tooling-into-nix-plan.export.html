Move the crew tooling into Nix, and make ./rebuild.sh own the order

Six npm CLIs, two curl | sh binaries and one self-updating clone are the last things on this machine that Nix does not own. This plan pins all of them, removes the clone-before-rebuild trap, and leaves firstmate as the one deliberately mutable tree with its expected commit recorded.

The one-sentence answer

Make ./rebuild.sh clone firstmate from your fork at a recorded commit before it builds, package the eight CLI tools as hash-pinned Nix derivations built from their published artifacts, and converge on one PATH answer — with legacy copies removed only after a one-week soak.

1 · What is true today

verified on this machine

Three provisioning paths, none hashed

  • ◆npm install -g writes five packages into /opt/homebrew/lib/node_modules.
  • ◆Two curl | sh installers download “latest” at run time and write into ~/.local/bin and ~/.no-mistakes/bin.
  • ◆node itself comes from Homebrew, while every other CLI dependency comes from Nix.

Nothing records which bytes the machine actually runs. The README’s version list is prose, and the install commands resolve a different version on the next machine.

The clone has to happen first, or the script is re-run by hand

Home-manager links firstmate/config/*, so activation creates ~/firstmate/config/. A later git clone refuses the non-empty directory. The README’s recovery is rm -rf ~/firstmate and clone again — a manual, destructive step a script can remove.

2 · Target: one owner per artifact

Nix owns every tool binary. Home-manager owns the profile and the link table. firstmate stays a git clone because it updates itself; the repo records which commit it expects and reports drift instead of enforcing it.

3 · The ordering trap, removed by the entry point

The trap is not that the clone is manual. It is that activation writes into the clone directory before the clone exists. Move the clone into rebuild.sh ahead of the build and the two orders collapse into one.

1 · Existing checkout

git -C ~/firstmate rev-parse --git-dir succeeds → touch nothing. Report HEAD versus the recorded pin.

2 · Missing directory

Clone the upstream, verify the pinned commit is an ancestor of the default branch, then reset --hard to it so self-update can still fast-forward.

3 · Home-manager stub

Directory exists but is not a repo. If it contains only links into the store and a config/ of links, move it aside, clone, then remove the backup. Any real file aborts with instructions.

Why a pin and not a hard lock: bin/fm-update.sh fast-forwards the default branch on /updatefirstmate. A detached HEAD or a rebuild that resets an existing clone would break the workflow the clone exists for. So the pin applies at clone time only; every later rebuild reports drift and does not move the tree.

4 · Packaging design

Two builders cover eight artifacts: an npm CLI built from its published tarball with a committed lock, and a release binary fetched by hash. Versions and hashes are data in one file, so bumping a tool is one edit plus the lever script.

File shape

nix/crew-tools/
  pins.nix          versions + per-system hashes (data, the only bump surface)
  builders.nix      npmCli and releaseBinary (two shapes, no per-tool copies)
  default.nix       reads pins.nix, returns the package list
  locks/<tool>/     generated package-lock.json, one per npm CLI
  update.sh         bump version → regenerate lock → refetch both hashes
crew-tools.nix      the one list home.nix imports (beside tools.nix)

tools.nix stays the dev-shell/formatter seam. The crew tools are a different seam: runtime user packages, darwin-only, and a 30 MB+ download the CI dev shell should not carry.

Lock policy

  • Source of truth is the published tarball users would get, not a repo build.
  • Generated once with npm install --package-lock-only --ignore-scripts; the lock records resolved URLs and integrity.
  • Pure at build: fetchNpmDeps gets the lock via postPatch; both the tarball and the dependency cache are fixed-output.
  • No rebuild: dontNpmBuild = true; the tarball already ships dist/.
  • No scripts: --ignore-scripts --omit=dev. Verified: all five CLIs print their version from this install.

5 · Changes from review

9 changes folded in

The design was approved with changes. This section records each one, what was checked, and where it lands in the rollout. Facts that were questioned are marked with the command that verified them.

1 · Hashes prove stability, not provenance

update.sh gains three gates before it writes a pin:

  • Refuse a version published in the last 14 days. Exact publish times come from npm view <pkg> time --json and the GitHub release timestamp.
  • Cross-check the Go binaries against the release checksums.txt (verified: both repos publish SHA-256 for all six platforms). For npm, run npm audit signatures in the lock directory.
  • Print the lock diff on every bump so transitive changes are reviewed, not just the top-level version.
Verified: npm audit signatures on a generated lock reports verified registry signatures and SLSA attestations for the transitive deps. It cannot attest the top-level tarball itself (no dist.integrity inside the tarball), so the tarball sha256 remains a separate pin.

2 · firstmate: fork and review

D3 stays report only for rebuild. Separately, the clone source becomes https://github.com/aditya-sathish-rao/firstmate (fork does not exist yet — create it in Unit 1). /updatefirstmate still fast-forwards, but to your fork. Upstream is added as a second remote; a bump means reading the upstream diff, merging into the fork, then updating.

The recorded pin is the fork commit. Rebuild reports drift against it; it never moves the tree.

3 · Declare the LaunchAgent in home-manager

Replace the guarded activation restart with launchd.agents."com.kunchenguid.no-mistakes.daemon" in home.nix, pointing at the store binary. The plist then updates with every bump and the GC hazard disappears.

Checked: the binary manages a plist named com.kunchenguid.no-mistakes.daemon.<hash>.plist via daemon start/uninstall. Home-manager must own that exact label; the installer’s managed service is uninstalled once in Unit 3, before the launchd agent is activated. If the binary rewrites it on daemon restart, the agent is reloaded from the store path after each bump and the check in Unit 3 catches a mismatch.

4 · Real offline command, not just --version

Unit 2 runs a real operation with npm_config_offline=true and a dead registry: gh-axi --help, tasks-axi --help, lavish-axi --help, chrome-devtools-axi open <local file> (with the MCP server from the store), and no-mistakes doctor.

Update checks are disabled in the environment: TREEHOUSE_NO_UPDATE_CHECK=1 and NO_MISTAKES_NO_UPDATE_CHECK=1 (both verified as real env vars in the binaries). The axi CLIs have no update-check env var; their update subcommands are explicit, not background. Any nag observed in the offline run is recorded and disabled if a setting exists.

5 · Pins cover Linux

pins.nix carries per-system hashes for aarch64-darwin, x86_64-darwin, aarch64-linux and x86_64-linux. Verified: both release repos publish checksums for all four. The npm CLIs are platform-independent. The same set feeds a Linux sandbox image; building it on a Mac needs a Linux builder (nix-darwin supports one).

6 · Clone over HTTPS

rebuild.sh clones the fork over HTTPS. On a fresh machine the SSH key and Automic Vault are not set up yet; a public repo needs no credentials. The fork must be public, or the clone step moves after the vault setup — that tradeoff is explicit in the ADR.

7 · Split Unit 3: switch, then soak, then delete

Unit 3a switches PATH and the launchd agent in one rebuild. Unit 3b is a separate, manual step after a one-week soak: remove the npm globals, ~/.local/bin/treehouse, ~/.local/bin/no-mistakes and the old ~/.no-mistakes/bin. Deletion is the hard part to undo, so it gets its own check.

8 · CI builds pins, and bumps are proposed

Add a macOS job that builds .#crew-tools when pins or locks change, with actions/cache on ~/.cache/nix. A scheduled workflow runs update.sh and opens a bump PR; the 14-day gate and lock diff make that PR reviewable. check --all still evaluates the fetch expressions on every push.

9 · Keep the repo out of agent reach

The Linux sandbox image does not mount the dotfiles repo. update.sh runs outside any sandbox, by a human. Otherwise an agent could edit its own pins — the exact failure mode this plan exists to remove.

Node 22 EOL, checked: the Node release schedule puts 22 (Jod) in maintenance since 2025-10-21 and at end-of-life on 2027-04-30 — spring 2027, as you recalled. All engine floors are satisfied by 24 (Krypton, EOL 2028-04-30), which is available in the pinned nixpkgs as nodejs_24 24.22.1. D4 is revised to nodejs_24, with a scheduled move to 26 before 24’s EOL.

Self-update commands hit a read-only store treehouse update, no-mistakes update and the axi update subcommands expect to replace their own binary. Wrap the two Go binaries so update prints the Nix bump path; document it in the ADR. firstmate keeps its self-update.
Daemon keeps an old path after a bump The LaunchAgent embeds the executable path; GC can collect the old store path. Restart in home.activation after links; verify the PID’s command line; uninstall the legacy service once.
PATH still answers with an old copy ~/.local/bin is prepended; npm globals sit in /opt/homebrew/bin. Unit 3 deletes both legacy locations and asserts every command -v resolves into the profile.
Firstmate reports wrong install instructions Its fm-bootstrap.sh suggests npm/curl commands when a tool is missing; the repo cannot edit a self-updating upstream. Tools are always on PATH, so the branch is not reached; README states that the suggestion is upstream text and the fix is ./rebuild.sh.
Lock regeneration becomes hand-edited drift The published tarballs ship no lockfile; locks are generated at maintainer time. update.sh is the only writer: bump, relock, rehash, run the gate. Committed locks plus fixed-output hashes keep builds pure.
Upstream deletes a release asset Go binaries are fetched from GitHub releases; npm tarballs from the registry. Fetch failure is loud at build time, never a silent version change. Re-pin to a live asset; optionally mirror later.
