Spec axis

No issue tracker or docs/specs/ file exists, so there is no formal spec to diff against. The de-facto spec is README.md plus the four ADRs and GLOSSARY.md. I checked the code against those claims directly.

  • ✓ opencode.json declares exactly the two providers README promises (DeepSeek direct + OpenRouter), both keyed from env.
  • ✓ crew-dispatch.json lists DeepSeek direct first, OpenRouter second, matching README's "preference, not live failover".
  • ✓ The opencode wrapper rewrites a rejected direct-key launch to OpenRouter, as documented.
  • ✓ cc and mate aliases inject secrets via av inject and set the OpenRouter base URL; the tracked settings file carries no env block (ADR-0002 upheld).

Deepening candidates

Shallow modules or leaky seams worth deepening, in recommendation order. Each card shows before/after.

A · Unify the file-type table in the check module

Strong in-process
files: .githooks/check
Problem. The same seven file types are encoded three times — a case, five formatter if-blocks, four linter if-blocks. Shotgun Surgery: a new type means edits in three places. And extension-less shell slips the net.
Solution. One table (extension / shebang → formatter + linter) drives classify, format and lint from a single loop.
  • · locality: type handling concentrates in one table
  • · leverage: one row adds a whole file type
  • · closes the opencode coverage gap

B · Give settings.json one author

Worth exploring in-process
files: home/.claude/settings.json · home.nix
Problem. ~/.claude/settings.json resolves through home-manager to the repo's tracked file, and the three … setup hooks commands append to it in place. The README even documents this. One file, two authors — repo intent plus installer side effects.
Solution. Render the declarative part like the VS Code settings (rendered map), and let installers write their hook block to their own file.
  • · locality: repo config changes for one reason only
  • · leverage: activation stays a pure merge
  • · stops installer version churn entering commits

C · Move the key probe behind the opencode seam

Worth exploring true external (mock)
files: home/.local/bin/opencode
Problem. The wrapper's one-call interface hides a ≤4s HTTP probe on every deepseek launch, and the 000-timeout path rewrites even when offline — contradicting its own comment. Dispatch and key-health are two reasons to change.
Solution. Keep the wrapper pure dispatch; cache the health probe (or run it once) behind its own seam so the probe is mockable and never on the launch path.
  • · interface hides less: no surprise latency
  • · locality: key-health logic concentrates behind one seam
  • · fix the 000-offline behaviour in one place

D · Inline the one-line tailscale module

Speculative in-process
files: tailscale.nix · configuration.nix
Problem. tailscale.nix is a pass-through: one line of interface, one line of implementation. The deletion test says inlining it concentrates nothing.
Solution. Inline services.tailscale.enable into configuration.nix — unless you expect the daemon's config to grow, in which case the file earns its place as a named seam.
  • · removes a speculative module
  • · decision hinges on whether tailscale config grows

Top recommendation

A — unify the file-type table in the check module. It's the repo's quality gate: the only imperative-logic module, and the one place where a small table removes the repeated parallel collections and closes the real coverage gap (home/.local/bin/opencode never being shellcheck'd). Highest leverage for the least churn.
